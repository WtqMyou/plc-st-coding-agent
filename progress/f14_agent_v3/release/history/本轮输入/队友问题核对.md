# 给队友的问题核对：先区分误判与模型错解

目前没有证据证明《STBench_F1.3_全库复核_最终工程》原题或参考程序有错误。已经确认的是本地平台适配分支、检查器的输入域问题，以及功能用例没有拒绝的两类模型错解。以下不要求为迁就模型答案而改题意，也不要求重做整套题库。

## 1. public-hard-04 公共FIFO：已确认的本地误判

原最终工程与本地题面都明确禁止同一调用中同时请求enqueue和dequeue。本地形式检查却生成以下轨迹，固定绑定容量2：

| 扫描 | enqueue | dequeue | reset | 模型elementCount | 模型status |
| --- | --- | --- | --- | ---: | --- |
| 1 | TRUE | FALSE | FALSE | 1 | 16#0000 |
| 2 | FALSE | FALSE | FALSE | 1 | 16#0000 |
| 3 | TRUE | FALSE | FALSE | 2 | 16#0000 |
| 4 | FALSE | FALSE | FALSE | 2 | 16#0000 |
| 5 | TRUE | TRUE | FALSE | 1 | 16#8002 |

第5拍不属于题目允许的调用。检查器据此用S4/N10-S4“满错误意味着计数等于容量”判违反，影响自研DeepSeek和Codex DeepSeek的首候选；两者当时功能均56/56，随后各触发一次形式反馈修复。这两个反例不能用于证明题内缺陷。

**由本项目处理：** 在检查环境编码`NOT(enqueue AND dequeue)`的输入假设，保持每个实例绑定容量不变，分别验证容量2和4。保留原始反例、修复提示和费用，不改原实验记录。队友无须为这个误判修改FIFO题意、参考算法或放宽状态码要求；也不能只删S4以掩盖非法输入。

证据：[自研DeepSeek](evidence/full_r8_20261110b/jobs/custom_deepseek-v4pro/public-hard-04.json)、[Codex DeepSeek](evidence/full_r8_20261110b/jobs/codex_deepseek-v4pro/public-hard-04.json)。这不是运行中缩容问题。

## 2. public-hard-04 公共FIFO：另有一条有效模型错误，可补功能回归

Codex MiniMax首候选通过56/56功能测试，但有效形式反例显示空队列出队报错后，下一个空闲扫描仍保留错误码：

| 扫描 | 输入与前提 | 应有输出 | 模型实际输出 |
| --- | --- | --- | --- |
| 1 | 新建空队列实例；dequeue=TRUE、enqueue=FALSE、reset=FALSE | elementCount=0，status=16#8001 | 符合 |
| 2 | dequeue=FALSE、enqueue=FALSE、reset=FALSE | elementCount=0，status=16#0000 | status仍为16#8001 |

该轨迹没有同时入队出队，违反原题“空闲调用无错误”以及S8（本地编号N10-S8）。原规约已能识别，不是规约写错。模型收到反馈修复后保持56/56，转为有界通过。

**建议队友处理：** 补充上述两拍功能回归，使用最终工程原接口绑定实际数组容量，不新增本地capacity接口。新用例应由原参考程序通过，并能拒绝“错误状态一直保持”的错解；作为新版本测试增强，不追写原分母。

证据：[Codex MiniMax FIFO答卷与反例](evidence/full_r8_20261110b/jobs/codex_minimax-m27/public-hard-04.json)。

## 3. public-hard-03 配方管理：模型并发请求处理错误，可补测试或明确策略

自研DeepSeek首候选通过19/19功能测试，但自行采用“查询 > 添加 > 删除 > 修改”的单分支优先级。以下两个新实例的首拍分别触发问题：

- 空数据库、合法非零recipeIn，同时令addRecipe和deleteRecipe出现上升沿。模型仅添加，recipeDeleted=FALSE且error=FALSE，违反原包S4。
- 同样的初态，同时令addRecipe和modifyRecipe出现上升沿。模型仅添加，recipeModified=FALSE且error=FALSE，违反原包S5。

S4要求每个删除沿当拍要么recipeDeleted，要么error；S5对修改沿同理。原最终工程中也有这两条公式，因此不是本地临时新增的要求。参考程序可以对未完成的请求报错，不能默默丢弃请求且不报错。模型修复候选仅16/19，冻结选择器保留第一份，最终功能通过但仍有形式违反。

**建议队友处理：** 若保留现有S4/S5语义，补并发请求的功能用例，并在题面明确每个请求必须成功或报错。不要直接把模型当前采用的优先级设为正确答案。若工艺要求实际上禁止并发或另有优先级，应先统一题面、规约、参考解、测试及输入假设，并作为明确的契约变更另立版本。

证据：[自研DeepSeek配方答卷与反例](evidence/full_r8_20261110b/jobs/custom_deepseek-v4pro/public-hard-03.json)。

## 4. public-easy-06 鼓风机：本地题面同步问题

最终工程已明确连续5次扫描、在第5次启动。本地题面仍写5秒，附带性质却使用5拍，参考程序也计5拍。这是本地合并时没有完整同步文字的问题，应由本项目统一表述；不是要求队友修改已明确的原版规则，当前结果也不能宣称验证了真实5秒定时器。

FIFO的VARIANT→DINT/capacity、板厚题的LTIME→LINT属于本地接口适配差异，目前没有证据说明队友原接口写错。详细来源比对见[公共题版本差异说明](evidence/full_r8b_public_source_comparison_20261111/公共题版本差异说明.md)。

本说明仅核对问题与建议，未改冻结题库、裁判、模型答卷或费用，没有新增模型调用。建议队友返回补丁、逐项说明及参考解/错解的验证结果，再决定是否采纳和补测。
