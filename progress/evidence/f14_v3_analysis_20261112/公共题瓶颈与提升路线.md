# 公共题瓶颈与提升路线

当前同口径为v4固定答卷工具纠错复评：公共22/80（27.5%），自建46/60（76.7%）。本轮仅分析，没有新增模型请求。

## 瓶颈证据

| 当前结果分类 | 题次数 | 主要含义 |
| --- | ---: | --- |
| 功能整题通过 | 22 | 已达到该题全部功能断言 |
| 功能阶段不符 | 37 | 持续输出、事件先后、时间单位、复位与边界等；少数含结构字段契约差异 |
| 原生编译失败 | 8 | 有真实CODESYS拒绝记录，仍需按首错分别定位 |
| 静态或接口失败 | 7 | 缺变量、未声明或不受支持的调用、代码未完整结束等 |
| 本地检查器未决 | 2 | 工序题中的匿名枚举、复杂嵌套CASE等，真实平台接受而本地子集未执行 |
| 无可评完整候选 | 4 | 当前这些记录主要来自睡眠中断，不等于已证明模型不会写 |

功能阶段的37项占58个未通过题次的63.8%。因此主要工作应转向需求契约、扫描状态与语义修复。即使按当前分类把其余21项全部转为通过，公共也只有43/80（53.8%），仍需解决大量功能阶段错误。

## 最有价值的切入点

- 灌装线：四组都没有整题通过，模型倾向把工序做成互斥状态，而公开要求中存在启动后持续工作的输出。需要先明确每个输出何时置位、保持与复位，避免自行增加关闭条件。
- 毫秒与纳秒、阈值当拍：果酱泵两份DeepSeek均19/20，差异集中在累计时间边界；MiniMax另有LTIME单位错误。
- 状态与操作顺序：配方槽位与配方ID、同拍操作优先级、机械臂与窑炉转换等，均需把公开要求转换为状态/优先级表。
- 近通过候选：另有去抖22/23、移动平均20/21、错误状态码7/8等。共5个题次仅差一条断言，适合先验证通用边界策略。
- 接口和环境能力：递归校验结构体字段及类型，例如RunComd与runCmd不等同；明确可用库与操作符，禁止凭空生成外部函数。原VARIANT平台约束继续单列，保持原题接口。

## 研发顺序

1. 免费补齐机械问题：匿名枚举和嵌套CASE的本地支持、递归结构接口校验、代码完整性与可用库清单，全部以独立正反控制验证。
2. 生成前产出简洁的工程契约表：输出保持/关闭条件、状态转移、同拍优先级、时间单位和边界，再生成ST。只使用公开题面及已确认约定，不从测试期望反推规则。
3. 改善语义反馈：失败输入与实际输出之外，关联被违反的公开需求条款，按不同故障簇选择代表轨迹；不提供测试期望或参考程序。
4. 用6类失败代表题做两模型两框架的24题次定向小试，定位改动收益；这属于诊断，不当作全公共题成绩。策略冻结后，再以20题统一对照验收。付费调用前重新精算预留，沿用210元总上限。

## 目标与判断

有明确提升空间，尤其是已定位的接口/执行缺口和近通过边界。公共整体接近自建76.7%意味着至少62/80、比当前再多40个成功题次；应作为实质性策略升级目标。先以公共约50%作为阶段目标，再争取70%—80%，以新生成结果验证，不直接承诺两套不同题集必然获得相同分数。

主力DeepSeek在自建15/15、公共自研6/20，说明需要加强的是从课程自然语言到精确程序行为的转换。增加并发已经解决耗时问题，继续提升准确率应优先投入这一环节。
