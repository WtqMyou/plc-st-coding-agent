## 3. 第三条：11 条 LTL 绑在实现内部变量名上，会让**整题形式分归零**

### 事实（我们已用实验证明，不是猜测）

公共题 114 条规约里，有 11 条 LTL 引用了**接口表之外**的变量：

| 题 | 规约号 | 引用的接口外变量 | 该变量实际是什么 |
|---|---|---|---|
| public-hard-02 | S2, S3, S4, S5, S7 | `phase` | 参考解内部状态机变量 |
| public-hard-02 | S4, S5, S7 | `curStation`, `dstStation` | 内部状态 |
| public-hard-02 | S6 | `compEdge`, `idx` | 内部边沿/步进 |
| public-hard-04 | S1, S4 | `cap` | VARIANT 缓冲容量 |
| public-medium-08 | S1, S2, S3 | `ok`, `segCount` | 内部解析结果 |

自建题 106 条规约：**0 条**有这个问题（你们如果只用自建题做诊断，碰不到这个坑）。

### 三层实验（`scratch/_spec_probe.py`、`scratch/_spec_rename_proof.py`）

1. **在参考解上跑这 11 条 → 全部"成立"。** 因为参考解里确实有这些变量名。所以这不是"连参考解都判不了"。
2. **把参考解的内部变量改个名（接口一字不动、行为完全等价、用例仍然 100% 通过）** → 规约立刻崩：
   - `phase→workPhase`：S2/S3/S4/S5/S7 全部 `SimError: 未定义变量 'phase'`
   - `cap→capacityNow`：S1/S4 崩
   - `ok→parseOk`：S1/S2/S3 崩
3. **爆炸半径**（最重要）：

```
参考解（7 条）  mc_error=""                                  total 7  hold 7  viol 0  incon 0
改内部名后      mc_error="模型检查器异常：SimError: 未定义变量 'phase'"  total 0  hold 0  viol 0  incon 0
```

**只要有一条规约的原子命题引用不存在的变量，`_attach_model_check` 抛出的异常会把该题所有 LTL 一次性清零（`mc_specs_total=0`），不是丢 1 条。**

还有一个反直觉的地方：如果那个未绑定变量所在的**分支在搜索中从不触发**，规约不会崩，反而**静默判"成立"**（`G(compEdge -> ...)` 里 `compEdge` 改名后，因为 `compEdge` 从未为真，蕴含式左件短路 → hold）。所以"规约过了"也可能是因为它根本没被执行。

### 建议

- **短期**：报告里不要报"LTL bounded_pass 47/175"这种绝对数就完事，要同时说明"其中 11 条绑定了参考解内部变量名，候选使用不同命名时会整题失去形式分"。这句话本身就是一条有价值的实验发现（LLM 的命名自由度与规约的可比性冲突）。
- **长期**：把我方这 11 条改成只观察接口量的写法。你方 `stbench/spec_policy.py` 里的 observer 方案可以直接借鉴，例如 public-medium-08：

```
G(NOT __spec_ip_valid -> ipValue = 0)
G(__spec_ip_valid -> ipValue = __spec_ip_value)
G(ipValue = 4294967295 -> __spec_ip_valid AND __spec_ip_value = 4294967295)
G(ipValue = __spec_ip_value)
```

我方接下来会做这一步，做完同步给你们。

## 4. 第四条：MiniMax 的输出截断与时间预算要把它们当同一个问题看

### 你们自己测到的事实

- 13/35 题返回 `length`，输出 token 用满 16384；
- 最坏样本：`completion_tokens = 16384`、**正文 0 字符**、`reasoning_content` 72779 字符 —— 推理把整个输出额度吃光，一个字符的 ST 都没写出来。
- 时间：单题 600 秒、每次请求前必须剩 450 秒，首轮生成+编译+检查超 150 秒后第二次请求无法开始；四组分别 14/16/29/20 题以"窗口不足"结束，**共 79/140**。

### 建议（按性价比）

1. **`max_tokens` 从 16384 提到 32768**（MiniMax 支持）；截断检测要区分"真的写不完"与"推理吃光额度"，后者应该触发**降低 reasoning 或换 non-thinking 模式**重试，而不是简单重试（重试会再吃一次 16384）。
2. **把 450 秒的剩余时间门槛降到 240 秒**，并把"编译+检查"的预算上限固定（例如每题最多 2 次请求、每次请求前只检查剩余时间）。现在 79/140 题根本没进修复轮，这个浪费比任何提示词优化都大。
3. **给"正文 0 字符 + 输出满额"单独打一个 `stop_reason=reasoning_exhausted`**，主表里分开统计。现在这 13 条和"模型写错代码"混在一起，会把 MiniMax 的语义能力低估。

| 标识符 | 次数 | 来源 |
|---|---|---|
| `IDLE` | 12 | self-medium-03 枚举成员 |
| `OPENING` | 11 | 同上 |
| `CLOSING` | 8 | 同上 |
| `E_GateState` | 4 | 同上（类型名） |

### 建议

- 提示词的硬性要求里加两条：
  1. 「中间变量（含边沿缓存、上升沿标志、计数器、状态枚举成员）**必须**在 `VAR` 段声明，一个都不许漏。允许用 `TYPE ... : ( ... ); END_TYPE` 定义枚举，枚举成员名可直接用在 `CASE` 里。」

## 6. 第六条：四道"只差一条用例"的题，具体差在哪

你们报告里说 public-hard-06（完成灯）、public-medium-04（加热状态）、self-hard-02（超时阶段）、self-hard-04（泵轮换）各只差一条用例。我方另外定位到两个自建题的典型错法，可直接用于改提示词或出针对性用例：

### self-hard-06 q10 —— 把不该算的位算进去了

```
输入: runRequest=true, pressure=4600.0, pressureValid=false,
      fuelFlow=4.5, steamFlow=5.0, outletCmd=90, outletFeedback=0, resetBtn=false
期望: tripLatched=true, currentCauseMask=1, latchedCauseMask=5
错误候选给出: currentCauseMask=5
```

题面写的是「bit1/bit2 只在 `runRequest` 且 `pressureValid` 且 `pressure >= 4500` 的超压工况下评估」，候选漏读了 `pressureValid` 这个前提。**这是一条"题面强调不足"的用例，我们会把它挪到题面的注意事项里。**

### self-hard-07 无扰切换 —— 两个输出都保持，不是只保持阀位

参考实现的行为是：模式切换当拍，`flowSP` 和 `valveCommand` **都不更新**（都保持上一拍值）。实测反例：

```
q10 → q11：flowSP 10.8 → 10，valveCommand 42.2 → 42.2（只 flowSP 跳变，因为 mode 从 2 切到 1 且当拍只把 oFlow 设成 manualFlowSP）
```

注意这里 `flowSP` 是**按目标模式更新**的，`valveCommand` 保持 —— 所以准确的规则是：

- 切到**非串级**（mode ≠ 2）：`flowSP := manualFlowSP`（预置型切换），`valveCommand` 保持；
- 切到**串级**（mode = 2）：两个都保持。

现有 S7/S8 已经是这个语义，但都用 `prev(normalMode)` 作前提，**连续切换的第 2、3 拍会漏检**（q19→q20→q21 就是这种）。我们试过去掉这个前提：

- `S7` 去掉后仍成立（参考解上 hold）→ **可以去掉**；
- `S8` 去掉后立刻被反例打掉（第 1 个快照，因为首拍 `prev()` 为 0 是边界）→ 需要配合"排除首拍"的写法。

结论：这条我们会改成「所有合法模式切换拍」并排除上电首拍，你们在报告里如果引用了 S7/S8 的原始版本，注意口径。

## 9. 追加（同日晚）：三条最新发现，直接影响你们报告里"形式化未判定"的口径

写完上面八节之后又做了三项实测，都有决定性证据。**这一节比第 3 节更要紧**，
因为它解释了你们 R8 四组 `bounded_pass` 只有 47/175、36/175、19/175、25/175 的

### 9.1 输入组合爆炸：名义 depth=8，实际只到 1–2 拍

`InputSpace.combos()` 是全笛卡尔积，BFS 每次迁移消耗一条 `mc_max_traces` 预算。
`_collect_domains` 又会把用例里出现过的所有输入取值都收进来，输入一多组合数就爆。
实测（`scratch/_mc_budget_audit.py`、`scratch/_mc_real_depth.py`）：

| 题 | 输入数 | 组合数 | 预算 | 名义 depth | **实际到达** |
|---|---|---|---|---|---|
| public-hard-05 | 18 | 262144 | 60000 | 8 | **1** |
| self-hard-06 | 8 | 44800 | 60000 | 8 | 2 |
| self-medium-05 | 7 | 42336 | 60000 | 8 | 2 |
| self-hard-07 | 8 | 21600 | 60000 | 8 | 2 |
| public-hard-02 | 11 | 10240 | 60000 | 8 | 2 |
| public-hard-06 | 12 | 10240 | 60000 | 8 | 2 |

后果：这 6 题的"成立"实际上只在 1–2 拍内成立。**报告里不能和其余题并列写成
"depth=8 有界检查通过"。**

### 9.2 public-hard-05 的 `truncated` 报的是假乐观值（我们已修）

组合数 262144 > 预算 60000，首拍展开就把预算烧光，BFS 循环体**一次都不进**。
原实现只在循环体内置 `truncated=True`，于是 `truncated=False` 被报了出来——
这是唯一对外暴露"结论强度"的信号，却给了乐观的假值。

修法（`stbench/modelcheck.py`）：循环结束后若仍有未展开前沿、且未抵达名义深度，
一律置 `truncated=True`。实测 hard-05 从 `trunc=False` 变为 `trunc=True`。

**请检查你们 fork 里同样的位置**：如果 `public-hard-05` 的 6 条 LTL 在你们结果里
是"bounded_pass"，那多半是同一个假信号，需要改成"仅单拍判定"或标为未判定。

### 9.3 一条规约引用不存在的变量 → 整题形式分归零（我们已修，你们也要修）

原来 `_atom_evaluator` 抛的 `SimError` 会一路传到 `_attach_model_check`，
被当成"模型检查器异常"，于是**整题所有规约**都变成 `mc_specs_total=0`：
一条规约的毛病，把另外六条本来能判的也一起清空了（实测 7 hold → 0 hold）。

我们把捕获下沉到**单条规约**：只把出问题的那一条标成"未判定"并写明原因，
其余照常判定。修完实测（public-hard-02，把参考解内部名 `phase` 改成 `workPhase`）：

```
原参考解       total=7 hold=7 viol=0 incon=0
phase改名      total=7 hold=2 viol=0 incon=5    ← 修复前是 total=0 hold=0
```

这和第 3 节是同一件事的两面：第 3 节说"别把规约绑在内部名上"，
这一条说"就算绑了，也不该因此把整题清零"。**两个都得改**，
否则你们那些候选的 `inconclusive` 里有相当一部分是被别人的规约连坐的。

### 9.4 建议：给大输入题声明显式输入域（`mc_inputs`）

我们的 schema 早有 `mc_inputs` 字段但从不读取，现已接线：
题目 JSON 可显式声明输入域，覆盖自动推断以收窄搜索空间。

验证（self-hard-06 收窄到 4 个真正影响足迹的输入，组合数 44800 → 64）：
深度从 2 涨到 **7/8**，注入的"丢位变异体"被抓到（`S13 违反@2`），参考解仍全成立。

代价：收窄等于声明"其余输入不影响被检查的性质"，这个声明要作者自己负责。
所以我们**默认不启用**，只在明知副作用时用。你们若要提高 `bounded_pass` 的分母，
这是最直接的一招，但报告里必须写清收窄了哪些输入、为什么那样收窄。

### 9.5 顺带：复审那 7 条意见的处理（与我们数据同步有关）

`self-hard-06` 的 S13 已由「足迹数值只增不减」改成**逐位精确累积**
（每一位：本拍历史位 = 上一拍历史位 OR 本拍线索位）。LTL 原子层没有 MOD/位运算，
所以用「枚举值集合 + `prev((…))`」表达——这个技巧是**从你们 v13 学来的**，
谢谢，很好用。用显式两拍轨迹（失效拍 → 过剩拍）验证：
参考解 `lcm=1,1,5,5` 成立，丢位变异体 `lcm=1,1,4,4` 在**第 3 拍**被抓。

`self-hard-07` 的 S7/S8 已采用你们的写法：去掉 `prev(normalMode)` 前提、
用 `prev(TRUE)` 表达"非首拍"，因此覆盖所有合法切换拍（含连续切换）；
并补上「阀位当拍保持」和「本拍不正常运算」。变异测试：旧式漏检，新式 `违反@2`。
