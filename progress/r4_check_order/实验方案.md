# r4两题形式检查顺序小试验

2026-11-08。比较功能测试失败后继续形式检查（always_mc）与仅功能通过后形式检查（tests_first）。两条件均使用冻结的r4数据、适配和裁判；唯一计划改变的是verification_after_tests开关。

题目预先固定为self-medium-03门控、public-hard-04 FIFO，沿用第三阶段预先选择的两题。这两题JSON与r2逐字节一致，不涉及本次三个工艺契约改动，也不将待签署的工业题当作已批准。全部候选重新生成，不复用旧答案或按结果重选题目。

只使用MiniMax-M2.7，受控自研框架与受控Codex CLI基线各跑两个条件、每条件两题，共8题次；每题最多初始生成加一次修复，最多16次上游请求。保留原有每框架提示，各框架自己的两个条件提示一致。模型参数、16384输出上限、420秒请求超时、450秒请求窗口、1200秒单题预算、CODESYS主口径与30秒形式检查预算保持一致。

不将请求窗口降为240秒：冻结求解器要求窗口覆盖请求超时，240小于420会破坏已有保护。此次也不提高token上限、不改变reasoning或反馈范围，避免同时改变多个因素。

每题先完成本地类型/接口及功能测试、所需CODESYS编译，再按条件决定是否执行形式检查。静态或原生编译失败均不执行形式检查。两条件的停止规则、允许最多一次修复、完整题目分母、工具异常分类一致。确认异常的规约不牵连其他性质；截断不能算完整有界通过。

费用沿用75元共享账本和原诊断累计44.011998元上限。本轮新增上限4.50元，实际累计上限取min(原诊断上限,准备时累计+4.50)。开始前必须为全部8题次各两次请求计算最坏预留并确认可覆盖；修复输入按131072字节上界保护，真实请求超过预留时在发送前阻止。保护未来各题的全部预留；未知费用保留并停止，不自动恢复或重试。

顺序采用两题反向排列，让每个条件各在前后位置出现一次。不能在仅两题、单次随机生成的样本上声称统计显著或框架稳定优势；除请求额度等计划变量外，模型自然生成差异仍是限制。主要指标为首轮/最终功能通过、修复新增通过、实际请求数、形式检查执行次数、墙钟时间、截断/空回复及模型费用；分别报告功能与形式结果。

启动前需要：r4完整性通过、针对性离线测试通过、真实Codex CLI的本地假响应通道通过、双平台正反编译控制通过、只读模型目录可用、源码和方案已推送GitHub、共享账本未变且无其他实验运行。本地演练不触达模型API，不写正式费用账本。

运行中若上游响应不确定、超时或费用异常，则保留已得结果、原请求和预留并停止，不自动重新发请求。完整8题次统计始终保留计划分母。机器需保持开机联网；状态页显示实时阶段，最终报告及证据同步GitHub。
