# 第八版请求剩余时间保护

## 已定位的问题

第七版于北京时间 2026-10-31 12:54 停止。开发阶段 MiniMax 的 FIFO 任务前四轮累计耗时约 587 秒，第五轮仍被发送，请求时限被缩成约 13 秒，随后触发上游墙钟超时。费用没有返回，账本保留该请求的 0.128472 元预留并停止全部付费调用。

失败原件位于 E:/PLC_Dev/evidence/real_experiments/campaign_75_repair_r7/develop_round_1/custom_minimax-m27/public-hard-04.json。原候选、费用事件、停止状态和冻结清单均保留。

## 修复规则

两框架共同采用完整的 450 秒请求窗口：上游时限 420 秒，加 CLI 开销 30 秒。整题仍为 600 秒、最多 5 个候选、输出上限仍为 16384 token。

每轮发送前重新计算剩余时间，包含此前的生成、裁判、平台检查、框架开销和本轮提示准备。不足 450 秒时，记录 insufficient_request_window，保存已有最佳候选并结束当前题，继续后续题目；不发送请求、不新增候选、不预留费用，也不触发全批次异常停止。最多 5 个候选是上限，时间不足时会提前终止。

求解器保存创建时的请求时限，后续轮次使用该值，避免一次缩短的时限污染后续调用。请求窗口与原始时限参与接续签名，窗口变化后拒绝混用旧记录。阶段汇总单独统计因请求窗口不足而结束的任务，保留完整题目和用例分母。

真正发生的上游超时、身份或用量异常仍保留费用预留并停止批次。本次修复不会将这些异常改为成功，也不解除当前账本停止状态。
