# 生成超时修复与第二版接入试跑

## 原因与策略

上一版 MiniMax FIFO 请求在 180.047 秒结束，错误为 `Upstream TimeoutError; no automatic retry`，未返回 token 用量。代码中有两处独立的 180 秒上限：MeteredProvider 的默认请求限制，以及 CodexProvider 对网关的再次压低。这比已确定的 600 秒整题上限短。不能仅凭这次客户端超时断定供应商故障或模型无法生成。

第二版配置把两框架共用的模型请求上限设为 420 秒，Codex CLI 额外留 30 秒收尾，整题仍限制 600 秒，编译单次 120 秒、LTL 60 秒，输出上限仍为 16384 token。没有更换模型、关闭思考模式或增加总预算。

HTTP 调用改为私有子进程，密钥只通过进程输入传递，不写入命令行、源码或日志。父进程对整个 HTTP 交换实施硬时限；即使上游持续发送心跳，也不能无限延长等待。超时后终止本地 HTTP 子进程并保留费用预留；上游是否最终计费仍以账单为准。OpenPLC 最佳候选复核也受整题剩余时间约束。

## 第三版：总输出上限与同协议比较

新目录为 `E:/PLC_Dev/evidence/real_experiments/campaign_75_limits_r3`。DeepSeek 两框架统一使用原生 Responses，MiniMax 两框架统一使用 Chat 桥接；模型、供应商、费用上限、思考默认设置和候选输出上限均不变。[DeepSeek Responses 协议](https://api-docs.deepseek.com/api/create-response/) 明确将 `max_output_tokens` 定义为可见输出与思考 token 的总上限，但 DMXAPI 通道是否遵守必须由小额实测确认，不能从官方协议直接推定。

增加 `limit-check --live`：每个模型只发送一次最大 512 token 的长输出请求，要求实际触达截断边界、返回完整用量且不突破上限；保存源码与配置哈希。正式候选请求必须有相同源码和配置的通过证据。Responses 的 `response.incomplete` 会保留其 usage 用于结算，不能因截断丢失费用，也不能把截断当成功候选。

本次已知超额只能通过与最新已结算事件直接关联的协议修复恢复，保留全部费用和未知预留，不复用身份恢复或超时恢复。恢复后先做 512 token 边界核验；若仍不遵守总输出限制，则停止该通道，不能靠扩大预算预留掩盖输出限制失效。第三版离线回归新增至 73 项。

第三版的 73 项回归、435/435 参考解用例及实际 Codex CLI 桥接全部通过。已执行与最新已知超额事件关联的协议恢复，费用 1.082141 元完整保留。随后两个真实边界请求均通过：DeepSeek Responses 的输出为 512 token、状态 incomplete；MiniMax Chat 的输出为 512 token、finish_reason=length，两者均有完整用量。该结果证明小额度截断路径可用，不计为生成候选成功。
