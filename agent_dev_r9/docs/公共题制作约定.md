# 公共题数据制作约定（成员 1 · 数据集构建）

> 本文件是给并行作业者的**唯一契约**。凡与本文件冲突的旧文档（AI交接文档.md 等）一律以本文件为准。
> 目标：让 20 道公共题（`datasets/public/public-*.json`）具备**参考解 + 测试用例 + LTL 规约**，
> 能通过 `scripts/check_dataset.py`（不带参数＝全部公共题）的硬性审计，且参考解在每个用例与每条 LTL 下都成立。

## 1. 每道题要交付什么

| 产物 | 路径 | 说明 |
| --- | --- | --- |
| 参考解 | `datasets/public/tests/<pid>.reference.st` | 单个 `FUNCTION_BLOCK`，英文标识符，只声明题目给的接口 |
| 测试用例 | `<pid>.json` 的 `test_cases` | 6~14 条，见 §4 |
| 形式化规约 | `<pid>.json` 的 `specs` | 3~6 条 LTL，见 §6 |

**判据（缺一不可）**
1. `python -X utf8 scripts/verify_one.py <pid>` → 编译通过、用例全过、`viol=0`；
2. `python -X utf8 scripts/check_dataset.py --pid <pid>` → 无任何 `✗`（硬性问题）。

## 2. 铁律：参考解先行，且不许为了用例改弱参考解

顺序固定：**读需求 → 写参考解 → 手工推演每周期期望值 → 写用例 → 跑 → 写规约 → 跑 MC**。

- 参考解必须逐条覆盖 `requirements` 里编号的需求（`(* R1: ... *)` 注释标注到代码位置）。
- 用例与参考解不一致时：**先怀疑用例**（期望值推演错了）；确认需求本身如此，才改参考解。
- 需求与 ST 能力冲突（§7）时：参考解取"最接近需求的工程实现"，并在该用例 `note` 与最终回报里**明确写出偏差**。不许静默改变语义。

## 3. JSON 写入方式

只改自己 pid 的两个键，不要重排其它键、不要动别的题：

```python
import json
from pathlib import Path
p = Path("datasets/public/public-easy-01.json")
d = json.loads(p.read_text(encoding="utf-8"))
if d["specs"] or d["test_cases"]:
    raise SystemExit("已被别人写过，先停下报告")   # 防止覆盖
d["test_cases"] = [...]
d["specs"] = [...]
p.write_text(json.dumps(d, ensure_ascii=False, indent=2) + "\n", encoding="utf-8")
```

`test_cases` 每条的完整字段（缺省值必须显式写全，保持格式统一）：

```json
{
  "tc_id": "e01-1",              // 题目内唯一；建议 <难度前缀>-<序号>
  "inputs": {"sensor": true},     // 本周期给值的输入
  "const_inputs": {"reset": false}, // 整个用例期间保持的输入（每周期都会重新写入）
  "expected": {"Pump_Motor": true}, // 非空；键名照抄题目 variables 的 name
  "note": "瓶子到位 → 泵启动",     // 中文一句话：场景 → 期望
  "init": {},                     // 单实例初值；只允许 0/FALSE 或 inout 数组/结构体
  "mode": "",                     // "" = 用题目的 case_mode
  "cycles": 1,                    // 本用例连续扫描几个周期，之后才断言
  "expect_full": false            // true 时必须断言全部输出变量
}
```

`specs` 每条字段：`{"sid": "S1", "text": "...", "ltl": "...", "kind": "safety|sequencing|liveness|data", "verified_by": "plcverif|simulation"}`。

## 4. 覆盖与量级（审计硬规则）

- **每个 `direction="output"` 的变量至少被断言一次**（可分散在不同用例）；inout 变量不强制，但能断言就断言。
- 每条用例 `expected` 非空；不得出现题目接口里没有的变量名；`tc_id` 唯一。
- 每个输入变量至少出现一次（否则是 warn，也说明漏测）。
- 量级：easy 6~8 条、medium 8~12 条、hard 10~14 条。
- 必测：正常路径、边界值（0 / 负值 / 上下限 / 类型边界如 16#FFFF）、互斥/优先级（急停压过一切）、复位与恢复、以及"不该动作时不动作"的负例。负例至少占 1/4。

## 5. 两种模式（决定用例怎么排）

- `case_mode="single"`（默认）：**每条用例一个全新实例**，跑完 `cycles` 个周期后只看最后状态。
  - 新实例初值只能是 0/FALSE；`init` 只对 `inout` 数组/结构体有意义。**不要**用 `init` 制造非零输出。
  - 需要"连续扫描 N 拍才动作"的题，就在单条用例里 `cycles: N`（例如去抖 3 拍 → cycles=3）。
- `case_mode="sequence"`：**所有 mode=sequence 的用例按列表顺序在同一个实例上连续扫描**，状态跨用例保留。
  - 只有"上一段轨迹的终态就是下一段的初态"（状态机、FIFO、计数器累积）才用它，并在 `note` 里注明"承接上一条"。
  - 用 sequence 时，题目的 `case_mode` 要在 JSON 里显式设为 `"sequence"`。

## 6. LTL 规约

- 算子：`G F X U`、`AND OR NOT ->`、比较 `= <> < <= > >=`、函数 `rising(x) falling(x) prev(x)`、数组安全 `no_array_overflow(...)`。
- `prev(x)` 只能出现在 `G(...)` 内；顶层用 `prev` 会恒不可判定。
- 变量名照抄 JSON 的 `name`。`text` 用中文写"当…时，必须…"。
- 至少 1 条 `safety`；尽量有 1 条 `liveness`（`G(p -> F(q))`）或 `sequencing`；数据聚合类（平均值、历史缓冲、排序）用 `verified_by: "simulation"` + 空 `ltl`，并在 text 里说清是"由用例验证的数据性质"。
- `verified_by="plcverif"` 的前提是**真的跑过 MC 且 hold**。

## 7. 平台能力边界（实测，2026-10-24）

- **TIME 字面量不可用**：`T#20ms` 解析为 0，TIME 加减恒为 0，`x >= T#200ms` 恒为 TRUE。
  → 计时/去抖类题（easy-04/05/06、medium-06）一律用**扫描周期计数**实现，用例按周期数断言，并在 note 里写"以周期数代替 DebounceTime"。
- **整结构体赋值不支持**：`io := localStruct;` 解析报"无法解析的语句"；**字段级读写**在多数上下文可用（`r := arr[i]; ok := r.field;` 已验证）。
  → 需要回写结构体 inout 时逐个字段赋值，并当心 `AND` 不短路（先判下标合法再访问数组）。
- **无 TON/TOF/R_TRIG**：边沿用 `e := btn AND NOT prevBtn; prevBtn := btn;`（先算后更新，顺序不能反）。
- `VARIANT`（hard-04）与 `LEN`/字符串索引/`STRING_TO_INT`（medium-08）已实测可用，不要沿用旧文档"做不了"的说法。
- 遇到确实写不出/读不到的接口：**停下该题**，记录最小复现片段 + 报错原文，回报给 Lead，不要改 `stbench/` 下的核心代码。

## 8. 环境

- Windows + 中文：所有命令前加 `python -X utf8`。
- 不要用 bash heredoc 写含换行的多行文件（`\n` 会被吃掉），用 python 脚本或 write 工具。
- 迭代时先用 `--no-mc` 快速过用例，最后再跑完整 MC。
